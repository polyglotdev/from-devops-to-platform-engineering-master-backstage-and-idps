What is Helm? Basics

Helm is a package manager for Kubernetes - just like apt for Ubuntu, brew for macOS, or npm for Node.js. It bundles all the Kubernetes resources needed to run an application into a single deployable unit called a Chart.

apt / brew / npm

Install software packages with dependencies handled automatically

Helm

Install Kubernetes applications with all resources bundled together

Package / Chart

A bundle containing everything needed to run the software

Installation / Release

A running instance of that package in your environment

Chart - The package (templates + defaults)
Release - A deployed instance of a chart
Repository - Where charts are stored

kubectl apply vs Helm Basics

Why not just use kubectl apply? As your application grows, managing raw YAML becomes painful. Helm solves real problems.

kubectl apply (The Hard Way)

kubectl apply -f namespace.yaml
kubectl apply -f configmap.yaml
kubectl apply -f secret.yaml
kubectl apply -f deployment.yaml
kubectl apply -f service.yaml
kubectl apply -f ingress.yaml
  • Different values per environment? Copy all files
  • No version tracking or rollback
  • Manual ordering of resources
  • Repetitive boilerplate

Helm (The Smart Way)

helm install my-app ./chart \ --set replicas=3 \ --set image.tag=v2.0.0
  • One command deploys everything
  • Override values per environment
  • Built-in release history and rollback
  • Templates reduce boilerplate
  • Dependency management

Chart Structure Basics

A Helm chart is just a directory with a specific structure. Click on any file to learn what it does.

my-chart/
Chart.yaml
The chart's metadata. Contains name, version, description, and dependencies. Think of it as package.json for your chart.
apiVersion: v2 name: fastapi-app version: 1.0.0 description: A FastAPI application appVersion: "1.0.0"
values.yaml
Default configuration values. These get injected into templates. Users can override these at install time.
replicaCount: 2 image: repository: my-registry/fastapi-app tag: latest service: port: 80
templates/
deployment.yaml
Kubernetes Deployment template. Uses Go templating to inject values.
replicas: {{ .Values.replicaCount }} image: {{ .Values.image.repository }}:{{ .Values.image.tag }}
service.yaml
Kubernetes Service template. Exposes your pods.
ingress.yaml
Kubernetes Ingress template. External access routing rules.
_helpers.tpl
Reusable template snippets. Define once, use everywhere. The underscore prefix means this file won't generate a manifest.
{{- define "myapp.fullname" -}} {{ .Release.Name }}-{{ .Chart.Name }} {{- end -}}
NOTES.txt
Post-installation notes. Shown to users after helm install. Great for providing access instructions.

Essential Helm Commands Intermediate

These are the commands you'll use daily when working with Helm.

helm install

Deploy a chart as a new release

helm install my-app ./chart -n prod

helm upgrade

Update an existing release

helm upgrade my-app ./chart --set replicas=5

helm rollback

Revert to a previous revision

helm rollback my-app 2

helm uninstall

Remove a release completely

helm uninstall my-app -n prod

helm list

Show all releases

helm list --all-namespaces

helm history

View release revision history

helm history my-app

helm template

Render templates locally (dry run)

helm template my-app ./chart

helm lint

Check chart for issues

helm lint ./chart

Release Management and History Intermediate

Every helm install or helm upgrade creates a new revision. Helm tracks the complete history, enabling easy rollbacks.

Revision 1

helm install my-app ./chart

Initial deployment with image:v1.0.0

STATUS: deployed
Revision 2

helm upgrade my-app ./chart --set image.tag=v2.0.0

Updated to new image version

STATUS: deployed
Revision 3

helm rollback my-app 1

Rolled back to v1.0.0 (safe state)

STATUS: deployed (rollback)
Advanced Concepts

Named Templates and Helpers Advanced

Define reusable template snippets in _helpers.tpl to avoid repetition. The underscore prefix tells Helm not to render this file as a manifest.

Define in _helpers.tpl
{{/* Generate standard labels */}} {{- define "myapp.labels" -}} app.kubernetes.io/name: {{ .Chart.Name }} app.kubernetes.io/instance: {{ .Release.Name }} app.kubernetes.io/version: {{ .Chart.AppVersion }} {{- end -}}
Use in deployment.yaml
metadata: labels: {{- include "myapp.labels" . | nindent 4 }}
Common Helper: Full Name
{{- define "myapp.fullname" -}} {{- printf "%s-%s" .Release.Name .Chart.Name | trunc 63 | trimSuffix "-" }} {{- end -}}
Result
# If release name is "prod" # and chart name is "fastapi-app" name: prod-fastapi-app

Conditionals Advanced

Use if/else to conditionally include resources or configuration. Toggle the switch to see how it affects the generated output.

Loops with range Advanced

Use range to iterate over lists and maps, generating repeated content.

values.yaml

env: - name: DATABASE_URL value: postgres://localhost/db - name: REDIS_URL value: redis://localhost - name: LOG_LEVEL value: info
DATABASE_URL
REDIS_URL
LOG_LEVEL

Template

env: {{- range .Values.env }} - name: {{ .name }} value: {{ .value | quote }} {{- end }}

Generated

env: - name: DATABASE_URL value: "postgres://localhost/db" - name: REDIS_URL value: "redis://localhost" - name: LOG_LEVEL value: "info"

Chart Dependencies Advanced

Your app needs a database? Declare it as a dependency and Helm installs it automatically. Dependencies are declared in Chart.yaml.

my-app

Your Application Chart

depends on

postgresql

bitnami/postgresql

bitnami/common

# Chart.yaml apiVersion: v2 name: my-app version: 1.0.0 dependencies: - name: postgresql version: "12.x.x" repository: "https://charts.bitnami.com/bitnami" condition: postgresql.enabled - name: redis version: "17.x.x" repository: "https://charts.bitnami.com/bitnami" condition: redis.enabled

Commands for dependencies:

helm dependency update ./my-app # Download dependencies helm dependency build ./my-app # Rebuild lock file

Best Practices

Helm Best Practices Best Practices

Follow these guidelines to create maintainable, production-ready Helm charts.

Chart Design

  • Keep charts focused - one app per chart
  • Use semantic versioning (1.2.3)
  • Document all values with comments
  • Provide sensible defaults
  • Include NOTES.txt with usage info

Values Organization

  • Group related values together
  • Use nested objects for complex configs
  • Never put secrets in values.yaml
  • Use values-prod.yaml for env overrides
  • Validate with JSON Schema

Security

  • Use Kubernetes Secrets for sensitive data
  • Set resource limits by default
  • Run as non-root user
  • Enable network policies
  • Scan charts with tools like Trivy

Testing

  • Run helm lint before committing
  • Use helm template to preview
  • Write tests in templates/tests/
  • Test upgrades, not just installs
  • Use CI/CD for chart validation

Dependencies

  • Pin dependency versions
  • Use conditions to make deps optional
  • Override sub-chart values via parent
  • Commit Chart.lock file
  • Audit dependency sources

Production

  • Always use --atomic for rollback on fail
  • Set --timeout appropriately
  • Use --wait to ensure readiness
  • Tag releases in git
  • Store charts in a registry (OCI or ChartMuseum)

Production Install Command

helm upgrade my-app ./chart \ --install \ --namespace production \ --create-namespace \ --atomic \ --timeout 5m \ --wait \ --values values-prod.yaml \ --set image.tag=$CI_COMMIT_SHA

--atomic: Auto-rollback on failure | --wait: Wait for pods to be ready | --install: Install if not exists (upgrade --install)
